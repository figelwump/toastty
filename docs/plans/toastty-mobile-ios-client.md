# Plan: Toastty Mobile — Native iOS Client

**Branch name:** `feat/mobile-remote-access-ios`, stacked on `feat/mobile-remote-access`
**Short name:** `mobile-ios`
**Created:** 2026-08-07
**Last revised:** 2026-08-14
**Status:** Approved — implementation in progress
**Depends on:** the revised mobile design doc (`toastty-mobile-design.md`, 2026-08-06). Its host Foundation → v0 → v0.5/v0.75 → v1 sequence is now implemented on `feat/mobile-remote-access` (gateway, pairing/auth, projection, Codex + Claude parsers, epoch-gated send, same-origin web client — ~10.2k lines with transport/race/security tests and smoke/QA evidence under `artifacts/remote-tests/` and `artifacts/remote-gui/`). The native entry gate below is therefore a short residual checklist, not a waiting game. Native code still does not become a second authority for the protocol: the host contract as implemented is the source of truth.

## Summary

Build the native iOS client for Toastty Mobile against the Remote Access Gateway contract that now exists and has survived the design doc's web-first gates. Reuse the proven parts of EmptyOS's iOS chassis — Tuist project shape, App/Domain module split, actor+reducer streaming patterns, explicit fixture/local/live modes, dispatcher scripts — and Plate's proven release and validation infrastructure — a TestFlight pipeline with 20 real green uploads, remote-Mac simulator validation, simulator auto-pick — while rewriting authentication and send reconciliation for Toastty's stronger device, epoch, and idempotency contracts. The UI implements the merged prototype's structure and dark skin with the desktop's exact five presentation statuses and Plate-style full-height chat sheet. The host's provider lifecycle, desktop presentation status, and input availability remain separate sources of truth: presentation status supplies terminology/color, while input availability alone gates the composer. Shared protocol types remain the canonical known-case encoding contract; a narrow native compatibility decoder supplies the tolerant behavior older clients need when the host adds optional wire variants.

The transport is WebSocket (host-decided and implemented; ADR recording is an entry-gate residual). The client is developed fixture-first against a pre-extraction host compatibility baseline plus explicit native evolution fixtures. The phase breakdown keeps read-only, transcript, and send validation separate so failures remain attributable. Native ships to TestFlight at the design doc's v1.5 milestone, keeping Tailscale as the only transport. Push/relay (v2) and remote approvals stay out of this plan.

## Locked decisions

1. **In-repo, separate Tuist project.** The app lives at `ios/` inside the toastty repo (EmptyOS/Plate monorepo style) with its own `Project.swift`/`Workspace.swift`. It is not added as an iOS target to the root `Project.swift`; the root manifest still gains the macOS `RemoteProtocol` target and dependency. The existing mac gate remains the mac build path and must compile the shared protocol on every relevant change.
2. **Shared protocol extracted from the host, with a dual-build viability gate.** The wire contract already exists in `Sources/Core/RemoteAccess/` (21 files, Foundation + CryptoKit only, no UI-state coupling). Phase 1 *extracts* the wire subset into `Sources/RemoteProtocol/` (Foundation-only, platform-neutral, Swift 6 strict): envelopes, session snapshot/cursor/page, states, input availability, pending interactions, journal events, send request/result, error codes, and the `RemoteDeviceScope` enum split out of `RemoteDeviceStore.swift` (the store itself stays host-side). Split the Foundation-only `AgentKind` value type into the shared target while leaving `ManagedAgentCommandResolver` and other host behavior in Core. `RemoteGatewayDeviceSummary` gains a field-based initializer in the shared target; its `RemoteDeviceRecord` conversion moves to a host-side extension so no device-store type leaks into the protocol target. Mac Core/App/tests then import the new target; budget for that churn. If cross-root Tuist paths, indexing, availability, or conditional-compilation friction appears, stop and promote the directory to a local SPM package before feature code accretes around the glob.
3. **Two iOS modules + tests, zero third-party dependencies.** `ToasttyMobileDomain` (.staticFramework: models, networking, reducers — no SwiftUI) and `ToasttyMobileApp` (SwiftUI). EmptyOS and Plate (~31k LOC each) both prove zero-deps is viable; keep it.
4. **Swift 6, strict concurrency, iOS 18 minimum.** Same as EmptyOS (Plate ships on 17, so 18 is a choice, not a necessity); no reason to diverge.
5. **Explicit fixture / local / live runtime modes from day one.** `TOASTTY_MOBILE_USE_FIXTURE=1` yields a fully offline deterministic app for previews, UI tests, and screenshots in Debug builds only. The primary `ToasttyMobileApp` scheme never sets it; the clearly named `ToasttyMobileApp-Fixture` scheme does. Missing configuration is an unconfigured pairing state, never an implicit fixture fallback. The baseline known-case fixtures are captured from the unmodified host at the native entry gate, before protocol extraction; Phase 1 proves the extraction preserves them and adds client-authored forward-compatibility fixtures. Live integration tests are `XCTSkip`-gated on env vars; credentials are injected only at test runtime and are never persisted into generated schemes or logs.
6. **The phone renders only the Toastty-owned projection.** No provider JSONL parsing, no terminal frames, exactly per the design doc. The client is provider-agnostic; Claude-vs-Codex differences never reach the UI layer.
7. **Input availability drives the composer; display status never does.** Additive optional summary fields carry the same exact presentation status and bounded status detail as the desktop. Older hosts without either field fall back conservatively from lifecycle state and input availability; unknown future values remain visible as unsupported data but receive no misleading state label or color.
8. **Approvals are read-only cards** with a "respond on the desktop" affordance until a provider semantic channel exists (design-doc policy).
9. **Design language:** the merged prototype's dark Toastty look — near-black surfaces, mono accents for paths/metadata, and the desktop's status palette (ready green, working brown, needs approval amber, error red; idle is visually quiet), in a hand-written Swift token file (no CSS-token generator unless the v0 web client and native end up sharing tokens).
10. **Accessibility identifiers on stable interactive elements** (`toastty-mobile-*`), following the EmptyOS convention. Dynamic Type is not capped app-wide; constrained metadata components may apply a documented local layout fallback.
11. **Tolerant decoding is client-side policy, not a silent host-model change.** Shared protocol types continue to encode and strictly decode the known v1 contract used by host tests. `ToasttyMobileDomain` first decodes raw discriminators: unknown stream messages are ignored; unknown journal events retain their sequence so the cursor advances but do not enter the rendered transcript; unknown display/input variants become explicit unsupported, read-only client states; unknown command results/errors fail the operation without dropping surrounding session state. This policy is fixture-tested at every enum boundary.
12. **The latest session snapshot is the live composer authority.** Journal `statusChanged` events preserve transcript-relative history, but local typing and accepted/uncertain sends can change coordinator availability without appending a journal event. Within one connection generation the client may seed from REST, then subscribes and requires the host's fresh full `session_list` snapshot to supersede that seed; WebSocket frames are consumed serially and work from older connection generations is ignored. Conversation handoff uses the inverse ordering: establish the subscription first, buffer matching event pages, then load the REST page/cursor and drain the buffer, matching the proven web client. `latestSequence` measures transcript catch-up only; it never orders composer availability.

## Approved execution refinements

The implementation review retained the product scope while narrowing the highest-risk transitions:

1. Phase 1 has two stop/go gates. Extract and validate `RemoteProtocol` against the frozen fixtures in both build graphs before implementing networking, reducers, or reconciliation. If the cross-root Tuist source path is unreliable, switch to the planned local Swift package at that gate rather than carrying both approaches.
2. The Phase 2 host-native-auth slice lands and passes browser-regression, migration, authorization-matrix, revocation, and stream-teardown tests before the iOS pairing UI depends on it. Client pairing and read-only screens follow as a separate checkpoint.
3. The native entry gate records the real headers received through Tailscale Serve, verifies missing and spoofed identity-header behavior, and documents the simulator-local exception before identity binding becomes an authorization dependency.
4. Manual fallback pairing requires an active Mac-created native offer, the existing short lifetime and single-use semantics, explicit entropy, identity-scoped attempt limits, and persistent lockout behavior sufficient to survive gateway restarts. QR remains the high-entropy primary path.
5. `/api/hello` is loopback-gateway-only, returns `Cache-Control: no-store`, never emits credentials or identifying data, does not enable permissive CORS, and has explicit incompatible-version and hostile-Origin tests.
6. Negative logging tests cover URLs and structured metadata as well as bodies and headers. Credentials, pairing secrets, hostnames, workspace paths, titles, and transcript content must not enter routine logs or diagnostics.
7. Connection cancellation tests explicitly cover concurrent refresh, background/foreground churn, conversation dismissal during paging, and socket-close races with REST completion. Unknown optional events are tested adjacent to status and interaction events so dropping one cannot corrupt cursor or composer state.

Data flow adopts, rather than blindly copies, the EmptyOS pattern: raw envelope → compatibility decoder → pure `Sendable` reducer (unit-testable, no async) → actor exposing latest-value state → screen controller → SwiftUI. State streams yield the current value immediately and use bounded `.bufferingNewest(1)` semantics; controllers may also request `currentState` directly. `ConnectionCoordinator` owns monotonic connection-generation guards, the session seed → subscribe → fresh-full-snapshot handshake, the conversation subscribe → buffered REST-page handoff, typed resume cursors, retry classification, jittered exponential backoff (1s initial, 30s cap), and scene transitions so the session and conversation runtimes do not grow independent auth/retry loops. A REST refresh or reconnect belongs to a new connection generation; its results cannot overwrite frames already accepted by a newer generation. The host web client (`Sources/App/Resources/RemoteWebClient/app.js`, 630 lines) is the working reference for tolerant decode, reconnect (1s→15s), visibility-driven refresh, and resnapshot handling — treat it as the behavioral oracle when fixtures are ambiguous.

**Send path (Phase 4):** compose → optimistic pending row with `clientRequestID` → `conversation.message.send(conversationID, clientRequestID, expectedInputEpoch, text)` → `accepted` / `rejected(reason)` / `uncertain` / `duplicate` → confirmed only when a normalized `userMessage` journal event carries that exact `clientRequestID` (the host normally echoes it in `ConversationUserMessagePayload`, with an `origin` field distinguishing local/remote). There is no content/timestamp fallback: identical desktop, retry, or multi-device messages must never confirm one another. `duplicate` means an earlier accept stands — treat it as accepted-pending-confirmation, not an error. `uncertain` closes the epoch host-side and suppresses retries; the client mirrors that and never silently retries on a new epoch. Host correlation is currently best-effort and in memory, so pending is not allowed to be infinite: when `projectionRunID` changes, or a completed resnapshot reaches `latestSequence` without the exact echo, the client removes the optimistic bubble and surfaces a terminal, dismissible `deliveryUnconfirmed` receipt (“Toastty could not correlate this send after reconnect — check the transcript”). It never auto-retries or attributes an `origin: unknown` message to the request. This receipt ledger is in memory only in v1.5; client process termination drops it, while canonical transcript events still reload normally.

**Transport:** WebSocket, decided and implemented by the host (`RemoteWebSocketFraming.swift`; web client `new WebSocket(...)` at `app.js:527`). `EventStreamClient` consumes the WS subscription (`session_list` full-snapshot rebroadcasts, `conversation_events` pages, `resnapshot_required`) behind the reducer-facing interface. Recording the transport ADR — including heartbeat cadence, idle timeout, and flow-control facts — is an entry-gate residual, not a client task. Browser cookie-authenticated commands retain their Origin/CSRF defenses host-side; the native client authenticates with a Bearer credential and is unaffected.

### Protocol compatibility and cursor scope (as implemented)

- **Versioning today:** responses and stream messages carry `protocolVersion: "1.0"`; current browser pairing, events, and send request bodies do not, and the host does not negotiate a client version. The entry gate therefore lands unauthenticated `GET /api/hello` before fixtures freeze, returning only `{ protocolVersion, minimumSupportedProtocolVersion, capabilities }` so a not-yet-paired native client can perform admission/version checks. Native pairing also presents the client protocol version and rejects an incompatible exchange. Other data requests need not duplicate the version after that admission check. A mismatch is non-retryable and produces a dedicated upgrade screen; the static-version-only alternative is removed from this plan.
- Shared known-case types remain strict. The native compatibility decoder handles evolution deliberately: unknown top-level stream messages are ignored; an unknown optional journal event is represented internally by its sequence/kind long enough to advance the cursor, then omitted from rendered state; unknown display or input variants become read-only `unsupported(rawTag)` client states with an explicit reason; unknown send outcomes or error codes terminate that operation with a generic non-retryable protocol error without discarding the current snapshot. Golden fixtures cover each policy independently so one unknown event cannot reject its whole page.
- **Cursor model:** the session list has no cursor — `RemoteSessionListSnapshot` (`projectionRunID`, `conversations`, `generatedAt`) is rebroadcast in full on change. Conversation paging and resume use `ConversationEventCursor(projectionRunID, projectionGeneration, afterSequence)`; a mismatch on run or generation yields `resnapshotRequired`. Per-conversation `projectionGeneration` bumps invalidate one conversation's cursors without disturbing others.
- **Projected status cannot race the transcript:** provider-derived `statusChanged` is itself a journal event in the same per-conversation sequence space, and each `RemoteConversationSummary` carries `latestSequence` so the client knows whether transcript state is caught up. Current composer availability is different: coordinator-only changes such as local draft invalidation and an accepted send arrive through the latest session snapshot and supersede historical journal availability for gating. The mandatory fresh `session_list` on subscribe plus connection-generation guards prevent a REST seed from reopening the composer; the subscribe-before-page buffer prevents a transcript event from falling through the conversation handoff. No new session-revision protocol field is introduced.
- **Retention is explicit:** pages carry `firstAvailableSequence` and `historyTruncated` for the bounded in-memory projection (10k events per conversation by default). A cursor below retention or from a stale run/generation produces `resnapshotRequired`; a same-run resnapshot preserves unmatched optimistic rows by `clientRequestID` while it catches up and never uses timestamps to merge them. A changed run, or a completed catch-up with no exact echo, converts the unmatched optimistic bubble to the terminal receipt defined above.
- **Clock skew:** snapshots carry `generatedAt` (and summaries `updatedAt`) as the server clock anchor; relative ages use monotonic elapsed time from receipt rather than device wall-clock comparisons.

### Native pairing and device authentication

Tailscale and Toastty provide separate layers. Tailscale Serve supplies tailnet reachability, HTTPS, ACL enforcement, and authenticated identity headers to a loopback-only gateway (verified: `NWListener` binds `.ipv4(.loopback)` only). Toastty issues an app-specific per-device credential for scopes, revocation, and audit. Live mode accepts a valid Tailscale Serve `https://<node>.<tailnet>.ts.net` origin; IP literals, self-signed live endpoints, and direct non-loopback gateway access are rejected. Local HTTP exceptions remain simulator-only development settings.

**Pairing UX:** the Mac's Remote Access preferences creates one native pairing offer and shows both a QR code and a short fallback code. QR scanning is primary; manual gateway + code entry is recovery. Use first-party Core Image to generate the QR and VisionKit/AVFoundation to scan it, preserving the zero-dependency decision. The QR contains a versioned, non-HTTP payload with the gateway URL, offer ID, 128–256-bit random pairing secret, expiry, and protocol version. It never contains the long-lived device credential. Avoid dispatching the secret through a custom URL scheme or ordinary HTTPS query, where another app, browser history, or access logs could capture it.

**Exchange:** `POST /v1/native-pairing/exchange` accepts either the offer ID/secret or fallback code, plus device name and protocol version, in the body. It is distinct from the browser pairing endpoint: browser pairing returns only an HttpOnly SameSite cookie; native pairing returns an opaque 256-bit device credential once. The native endpoint does not accept a browser session cookie and rejects browser-origin/fetch-metadata requests. Pairing offers are native-client-bound, single-use, expire after two minutes, are rate-limited, and invalidate both QR and manual-code paths when either succeeds. The host records the `Tailscale-User-Login` supplied by Serve and compares it on every native Bearer request and WebSocket upgrade. Live native pairing rejects a missing identity header; simulator-local mode has an explicit test-only exception.

**Scopes:** native pairing grants `read` + `send`, matching the host's default-on policy (commit `2e8e16db`: browser pairing grants read+send; per-session remote writes default on with a process-local per-conversation disable on the Mac; device scope remains the durable remote-send kill switch). Scope changes stay on the Mac. The write-disabled and read-only composer states remain fully implemented as the exception paths.

**Storage and requests:** the phone stores the credential with `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, appropriate while background streams are suspended. The host stores only its hash in a device record containing `deviceID`, name, optional Tailscale login, scopes, created/last-seen timestamps, and revocation state. `tailscaleLogin` is an additive optional field with custom legacy decoding: existing browser-paired records decode it as nil and remain valid; newly paired native devices must have a non-nil login. Every native request and stream handshake sends `Authorization: Bearer <credential>`; credentials never appear in URLs, routine logs, diagnostics, or generated schemes.

**Lifecycle and authorization:** the v1.5 credential is long-lived until unpair/revoke; there is no refresh endpoint or copied refresh actor. Rotation means re-pairing. Authentication mode is selected centrally before route authorization: a browser cookie requires the existing exact Origin checks; a native Bearer credential permits an absent Origin, ignores any cookie, and still rejects a present non-allowlisted Origin. This matrix applies to session list, event paging, send, revoke/unpair, and the WebSocket upgrade rather than being reimplemented route by route. `401` means missing, invalid, revoked, or Tailscale-login mismatch and stops automatic reconnect before returning to pairing. `403` means the credential is valid but device scope or session write authorization denies the operation; it does not clear the credential. Scope changes occur on the Mac by updating the device record, so the token need not change. Revocation closes every active stream indexed by `deviceID` immediately, then rejects reconnects. Phone-side unpair performs a best-effort revoke before deleting the Keychain item; Mac-side revoke remains authoritative. Tailscale strips spoofed identity headers on remote Serve traffic, but a local process can forge loopback headers; the per-device Bearer credential remains the actual authority and login binding is defense-in-depth inside the existing “local processes are trusted” host threat boundary.

## UI/UX specification

### Status model → UI presentation

`RemoteConversationSummary.presentationStatus` carries the same five-state presentation value the desktop computes for a panel. Its additive optional `statusDetail` carries a separately bounded, sanitized excerpt of the desktop row's real detail; the shared Home card uses that excerpt before a pending-interaction preview or legacy availability fallback. Presentation remains intentionally separate from the provider lifecycle and four input-availability variants:

| Presentation status | Dot | Notes |
| --- | --- | --- |
| **ready** | green | ranked after errors; input availability independently decides whether the phone can reply |
| **working** | brown | active desktop work, shown with a spinner and italic detail |
| **needs approval** | amber | ranked after ready; approval remains read-only on the phone |
| **error** | red | highest-urgency Activity bucket |
| idle | none | compact, visually quiet card with no status header |

Both presentation fields are additive and optional. A client connected to an older host conservatively maps `starting`/`working` to working, `awaitingInput`/`ready` to ready, `interrupted`/`error` to error, and `ended`/`offline` to idle; without `statusDetail`, the card falls back to a pending request or existing availability copy. An unknown future presentation value receives no label or color rather than being guessed. Activity is flat and ordered error → ready → needs approval → working → idle with recency inside a bucket. Workspaces uses the same card and within-group order, while groups are ranked by their most urgent member. The host contract defines valid lifecycle/input combinations rather than a Cartesian 8 × 4 state machine. The client handles an unexpected combination safely by rendering both facts and disabling input unless availability is a recognized `openPrompt(epoch)` and device/session authorization also allows send. Note: Claude conversations currently never publish `openPrompt` (`unavailable(unknown_provider_state)` — no authoritative prompt-open signal in the transcript; hook-based enablement is a proposed later host slice), so a permanently read-only live conversation is a first-class case, not an edge case.

### Composer gating (input availability → compose bar)

| Input availability | Compose bar |
| --- | --- |
| openPrompt(epoch) | enabled; placeholder "Message {agent}…"; send carries the epoch (`bindingID` + `counter`, opaque to the client) |
| unavailable(working) | locked: "{agent} is working — input opens at the next prompt" |
| unavailable(other reason) | locked: reason-specific copy; generic fallback "input not available" |
| pendingInteraction | locked: interaction card pinned above composer, "respond on the desktop" |
| localDraft | locked: "✎ paused — a draft is in progress on the desktop" |
| session write-disabled / read-only device scope | locked: "remote input is off for this session — enable it on the Mac" |
| offline/ended | locked: "session offline — resume from the desktop" |

Send failures render as inline, dismissible rows under the optimistic message: stale epoch ("the prompt changed — review and resend"), local draft race, scope denial, uncertain ("delivery unconfirmed — check the desktop" with the idempotent-retry note). A `duplicate` response is not a failure: the earlier accept stands, so the row stays in pending-confirmation state until exact journal confirmation or terminal `deliveryUnconfirmed` reconciliation. On that terminal transition the optimistic bubble is removed, canonical transcript messages remain untouched, and a compact receipt explains that the client could not correlate the send. An uncertain or unconfirmed send is never silently retried on a new epoch.

### Screens

**Pairing/onboarding.** First-run: explain the model (one sentence), primary [Scan QR Code] action, and secondary [Enter code manually] path. The QR supplies the gateway and high-entropy one-time offer; the manual path accepts a Tailscale Serve hostname plus the short code shown by the Mac's preferences pane. Before exchange, show the authoritative hostname and ask the user to confirm. Success stores the opaque device credential in Keychain (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`); the device pairs with read and send scopes (host default); scope changes stay on the Mac. Failure states distinguish bad/expired/consumed offer, Tailscale disconnected, host asleep/unreachable, TLS/hostname failure, identity mismatch, and protocol version mismatch.

**Home.** A custom header contains TOASTTY, the connection pill (live / reconnecting / offline), and Settings. Section 1: `READY · n` — one card per ready session across all workspaces. Section 2: `NEEDS APPROVAL · n` — read-only approval cards. Each action card contains workspace · agent · age, session title, and an input-availability reason. The reason is derived from authoritative input availability: openPrompt → “Ready for your reply”; localDraft → “Draft in progress on the Mac”; pendingInteraction → an optional prompt/question preview, falling back to “Waiting for a response on the Mac”; unexpected unavailable → a safe generic reason. Tapping the entire card opens chat and focuses the composer only when input availability permits a reply; there are no nested Open/Reply controls. `WORKSPACES` contains one card per workspace (grouped client-side from `placement.workspaceID`/`workspaceTitle`): name, roll-up pill (n ready / n need approval / n working / quiet), mono path, and up to 3 session mini-rows (status + title + age + draft badge). “+n more” expands and collapses that card in place. Tap the workspace header → workspace screen; tap a mini-row → conversation screen directly. Pull-to-refresh starts a new connection generation whose stream-delivered full snapshot supersedes its REST seed rather than racing the old stream.

**Workspace.** Back header (name, session count, path). Session rows sort ready → working → needs approval → error → idle. Non-idle rows show the desktop status label/color; idle remains visually quiet. Rows also show agent tag (mono, colored), title, age, last-activity line, and badges (✎ desktop draft, ⏸ write-disabled). Tap → conversation screen and focus the composer when input is allowed.

**Conversation screen** is pushed full-screen on the app's `NavigationStack`. Its inline navigation-bar header shows title, workspace · agent, and presentation status; the system back action returns to the prior screen. Transcript rows, all from journal events: user message (right bubble; `origin` distinguishes local vs remote), assistant message (left, borderless, markdown via the EmptyOS renderer; `phase` may distinguish commentary vs final), compact tool-batch card (consecutive tool rows grouped by `callID`; tap opens their summaries and selectable details in a scrollable medium-detent sheet), interaction card (kind icon, prompt, options rendered read-only, state pending/resolved/superseded), status/binding markers (thin centered rows: "session resumed", "interrupted"), subagentSummary (collapsed row). Scroll system copied from EmptyOS: live-edge follow, jump-to-latest pill, post-layout coalesced scroll. Paging backward via `conversation.events.get` when scrolling up. `resnapshotRequired` → non-blocking overlay "resyncing…" → rebuilt transcript, scroll position best-effort. Composer per gating table. User-initiated navigation to the conversation requests keyboard focus after the push transition and composer are ready; deep links do not summon the keyboard.

**Settings.** Connection (host, tailnet reachability, protocol version, projection run ID / generation, active conversation cursor), This device (name, scopes, credential created-at; "unpair" = best-effort revoke followed by local credential wipe), Diagnostics (redacted connection log ring buffer — no transcript content, titles, workspace paths, credential material, or pairing secrets; os.Logger categories toggle), About. Device *management* (scope grants, per-session write disable, kill switch) stays on the Mac per the doc; Settings links to it descriptively.

**System behaviors.** Scene-phase: background → suspend streams; foreground → `connectIfNeeded()` + cursor-aware snapshot refresh (EmptyOS `ListRefreshLifecycle`, 30s debounce). Refresh starts a new connection generation, discards callbacks from older REST/socket work, and waits for the new subscription's full session snapshot before declaring state live. Conversation paging starts only after that subscription exists and buffers matching event pages until the REST cursor is established. Retryable network failures use jittered exponential backoff; a reconnect banner appears after 2 failed attempts and offers a manual reset. `401` and protocol mismatch never loop. Deep links are parsed by a pure `DeepLinkParser`; production, development, and prod-test builds use distinct schemes (`toastty-mobile`, `toastty-mobile-dev`, `toastty-mobile-prodtest`) so installed builds cannot claim the same route (Plate learned this the hard way with auth-callback scheme collisions).

**Accessibility.** Status is never conveyed by color alone (dot + label). Support all Dynamic Type accessibility categories; compact pills may change layout or hide secondary decoration but never cap the app globally. VoiceOver labels: "{title}, {bucket}, {workspace}, {age}". Composer lock reasons are announced. QR pairing has a complete manual alternative and does not require camera access.

## Edge cases

Client compatibility policy additionally covers unknown event/message/state/input/result variants without changing strict host decode behavior. Client-specific additions: QR photographed but expired/consumed; QR secret never exchanged because Tailscale is off; missing or changed Tailscale identity; a legacy browser credential with no bound login; credential revoked mid-stream (server closes it → reconnect receives 401 → pairing, no refresh); scene-phase churn; jittered backoff cancellation; send while backgrounding; optimistic send surviving a same-run resnapshot; host restart or completed resnapshot with no exact send echo (optimistic bubble becomes a terminal receipt); client process termination drops the in-memory receipt without replaying the send; session-list snapshots and per-conversation sequences advancing independently; older REST results arriving after a newer stream update; `duplicate` send responses after reconnect retries; huge single messages (cap rendered height with accessible expand); clock skew (snapshot supplies `generatedAt`, then relative ages use monotonic elapsed time from receipt rather than device wall-clock comparisons); all Dynamic Type reflows; hostname change; tailnet up but Mac asleep; TLS/hostname failure; valid credential with revoked send scope; and a provider (Claude today) whose live sessions never open the composer.
